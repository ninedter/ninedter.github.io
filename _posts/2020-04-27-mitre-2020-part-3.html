Modifier Detection Category (附屬偵測類別）

首先， Modifier 這個字其實本義不是附屬，而是一個加強或是修正的意義。但是我為何決定要稱為附屬偵測類別的原因，也是因為在這次的測試中， Modifier 最主要是拿來做主要偵測類別的加強輔助。換句話說，當廠商在每一次測試中被給予一個主要偵測類別的辨識，如果有需要補充的話，就會用附屬偵測類別去執行。

回到我們昨天這張圖，你可以看的出來，在主要跟附屬偵測類別中，附屬偵測類別的輔助，可以更佳的說明該廠商測試的時候，是如何發現這個攻擊，或更快的瞭解他們能提供什麼訊息做辨識。

所以在每個主要偵測類別被給予到某一個測試項次上的時候，如果有需要補充的地方，就會以輔助類別去補充。但如果沒有，則該測試中的主要偵測類別就沒有輔助類別。值得去注意的是，每個廠商針對不同的測試項目，都有可能會有不一樣的偵測方法，這其實在看各家廠商的報告時，也蠻有趣的。

而如果有注意到 MITRE 上一輪的驗測的話，你會發現這一次跟上一次的輔助類別有一些不同。有一部份的原因是因為兩次測試的方法和方式其實有所不同。因此再上一輪 APT3 的測試中的許多輔助類別其實都被拿掉，或是在這次測試中合併為單一的輔助類別去加以解釋。

而整體上來說，測試的結果，不管是在於哪個測試項目，多半會有輔助類別去加以說明。不管是主要類別中的結果如何，輔助類別可以協助多瞭解MITRE 在於結論上是如何進行總結的。

那我接下來就幫大家解釋一下，輔助類別的意思

輔助偵測類別說明（翻譯自 MITRE ATT&CK Evaluation Detection Categories）

Alert （警告）: 將資料轉換成為優先的通知予分析人員，該通知必須為某可疑或確認的活動，並需要更進一步的分析（如：圖示、凸顯、跳出視窗等）。不屬於遙測的的附屬類別。

範例：
* 在儀表版上有一個視覺化通知或警告訊息通知「橫向移動」有發生。
* 一個可被辨識的確認標的呈現在儀表版上並可讓分析人員知道高風險性的活動可能已經發生。

Correlated （關聯）: 資料是由先前所觀測到的可疑/惡意活動所發出的警告或由分析人員所看到的高可疑性動作相關的活動而產生。關聯證據的範例包含標示當下測試的攻擊技術的進程執行樹或一連串活動中所標示出與可疑/惡意活動有關係的資料。

範例：
* 一個進程執行樹或一串的活動顯示 net.exe 和先前出現的「憑證輸出」活動相關。
* 一個在儀表版內觀測的結果看出一個由 ipconfig.exe 與先前告警的一個 IOC 有關係。

Delayed （延遲）: 偵測結果（警告、觀測、戰術、技術等）因某些原因而延遲或無法提供給使用者，例如該顯示的結果需要另外經過其他的處理後才能形成該活動的偵測結果。延遲類別並不會被賦予至只花到短時間提供結果給使用者的正常自動資料收容或例行的資料處理，或甚至包含非廠商系統本身處理能力問題而造成的連線異常結果（例如：網路延遲）。延遲輔助類別都會增加說明是什麼原因造成延遲。

延遲被分為以下類型：

Manual （手動）- 資料處理是由人員啟動而並非自動處理。在所有的 MSSP 類別中，由廠商分析人員檢查並產生的資料結果在之後提供給 MITRE 分析人員。

Processing（處理）- 活動偵測因為需要符合更複雜的判斷邏輯而產生其他的資料處理時間而延遲將結果提供給 MITRE 分析人員。

範例：
* 廠商的雲端服務元件使用機器學習並在紅隊執行「憑證輸出」攻擊後經過了幾個小時後才觸發該活動警告。這個偵測結果就會被給予一個主要偵測類別內的「技術」（Technique）偵測但會附帶一個「延遲-處理」的輔助類別結果。
* 廠商將資料回傳至分析團隊，並在紅隊攻擊執行完成後三個小時後完成處理原始資料並產生一個「偵測到惡意活動」的警告在介面上。這個偵測會收到主要類別內的「人工分析」（MSSP）偵測但會附帶一個「延遲-手動」的輔助偵測類別。

Host Interrogation（主機審視）: 由廠商本身產品功能從端點直接將資料拉出。此類別表示通過手動分析從未被自動收集的資料中去辨識出可能的行為，並通過向分析人員顯示特定於當下被執行的攻擊行為發生時所出現的活動有進行了分析。雖然對某些資安團隊這個功能蠻有用的，但是透過這個方法去收集資料有時會比較困難，也會因分析人員的能力等級去解析這些資料並提供可反應的方案。主機審視這個輔助類別只會被賦予「無偵測」（None）的這個主要類別。它將被標記為延遲，以與其他延遲檢測保持一致。

範例：
* 原廠產品中有一個遠端指令介面的元件可以將作業系統的日誌從有可能被攻擊的主機中拉出做更進一步的分析。

Residual Artifact（殘留證據）: 需要進行額外分析以確定可能已使用了哪些功能或行為的資料（例如二進製或進程記憶體）。 此類別表示通過手動分析從未被自動收集的資料中去辨識出可能的行為，並通過向分析人員顯示特定於當下被執行的攻擊行為發生時所出現的活動有進行了分析。所收集的數據更多是對抗行為的副產品，而較少表示對抗行為。 雖然對某些資安團隊這個功能蠻有用的，但是透過這個方法去收集資料有時會比較困難，也會因分析人員的能力等級去解析這些資料並提供可反應的方案。 殘留證據這個輔助類別這個輔助類別只會被賦予「無偵測」（None）的這個主要類別。 它將被標記為延遲，以與其他延遲檢測保持一致。

範例：
* svchost.exe 進程記憶體因為被認為有可疑活動而被收集並在後續去進行分析。之後由線向分析發現在該系統中可能有 keylogger （資料收集器）在該系統中。
* PowerShell 腳本在執行時自動被收集。後續分析發現該腳本有能力存取使用者桌面的螢幕截圖。

Configuration Change（設定更改）: 該廠商的設定從一開始評估時有進行了修改。這可能是因為要收集或處理更多的資料。設定更改的輔助類別在使用時會與其他輔助項次配合去進行更詳細的解釋。

設定更改被分為以下類型：

UX （介面）- 廠商本身的偵測功能並未修改，而修改使用者介面。這個修改可包含要顯示某種已被收集，但未呈現給使用者看的資料。

Detection （偵測）- 廠商本身收集或處理資料的功能可能因收集或處理不足進行修改。修改可能包含在偵測端的軟體修改設定收集新的資料，或於資料處理端修改處理邏輯去做新的判斷。

範例：
* 帳號創建的資料有在後端收集但在預設狀況並沒有在使用者介面呈現。廠商修改後端設定並允許該「觀測」（Telemetry）的帳號創建結果在使用者介面上呈現。因此「觀測」主要類別會被給予至該「帳號創建」的「技術」（Technique）偵測，並加上 「設定更改-介面」（Change-UX） 的輔助類別。
* 廠商修改設定並在 foo，foo1 和 foo2 執行時加上新的標註「發現」（Discovery）。「戰術」（Tactic）和「設定更改-偵測」Configuration Change-Detection）會被給予至該偵測項目（與修改前為 「觀測」（Telemetry）不同）。
* 規則或檢測邏輯被創建並追溯回該測試，或者稍後進行重新測試以顯示廠商產品有該工能。 這將用輔助類別「設定更改-偵測」（Configuration Change-Detection）進行標記。
